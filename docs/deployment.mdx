# Deployment

This page covers the provider runtime contract and the supported operator deployment paths.

## Supported deployment modes

Use one of these:

- Docker Compose for standalone Omni or VM-based environments
- Helm for environments where Omni already runs in Kubernetes

## Validated topology

The live-validated path is a single Ubuntu host running:

- OpenNebula `7.0.1`
- Omni `1.6.0`
- `omni-infra-provider-opennebula` as a standalone container

This topology is documented in detail at [/live-lab](/live-lab).

## Production stance

- Run a single active provider instance per OpenNebula trust boundary.
- Keep provider config on disk and secrets in environment variables or an env-file.
- Expose `/healthz`, `/readyz`, and `/metrics`.
- Prefer provider-managed image import only when artifact and checksum URLs are configured.
- For backend Ceph and datastore provisioning, use the public Ansible workflow documented at [/runbooks/ceph-opennebula-storage](/runbooks/ceph-opennebula-storage).

## Container image

Use:

```text
docker.io/nudevco/omni-infra-provider-opennebula:<tag>
ghcr.io/sparkaiur/omni-infra-provider-opennebula:<tag>
```

## Required inputs

- Omni API endpoint
- Omni service-account key
- OpenNebula endpoint in the provider config file
- One OpenNebula auth mode
- Allowed templates, datastores, and networks that match your OpenNebula inventory

## Docker Compose

The standalone deployment files live under:

- `deploy/docker-compose/compose.yaml`
- `deploy/docker-compose/.env.example`
- `deploy/docker-compose/provider-config.yaml.example`

Use this mode when:

- Omni and the provider run on a host or VM
- you want config and secrets mounted from disk
- you want the simplest staging or lab deployment model

## Helm

The Kubernetes deployment files live under:

- `helm/omni-infra-provider-opennebula/`

Use this mode when:

- Omni already runs inside Kubernetes
- you want values-driven provider rollout
- you want metrics exposed through a Service and optional ServiceMonitor

## OpenNebula auth

Supported auth environment variables:

- `OPENNEBULA_SESSION`
- `OPENNEBULA_USERNAME`
- `OPENNEBULA_PASSWORD`

## Provider config example

Use the full example at [/examples/provider-config](/examples/provider-config). The minimal shape is:

```yaml
providerID: opennebula
opennebula:
  endpoint: "https://opennebula.example.com/RPC2"
  templateName: "talos-omni-base"
  hypervisor: "auto"
defaults:
  flavor: "small"
  firmware: "uefi"
  networkContextMode: "auto"
  hostnameStrategy: "cluster-role-sequence"
features:
  allowExplicitResources: true
  enableGPU: false
  hardDelete: false
timeouts:
  instantiate: 2m
  vmReady: 10m
  terminate: 5m
flavors:
  small:
    cpu: "2"
    vcpu: 2
    memoryMiB: 4096
    rootDiskGiB: 40
```

## Validation after deploy

After deploying the provider:

1. confirm `/healthz`, `/readyz`, and `/metrics`
2. register or reconnect the provider in Omni as `opennebula`
3. create a machine class with `grpctunnel: ENABLED`
4. provision one machine and confirm:
   - the OpenNebula VM name matches the Talos hostname
   - the VM is rendered with the expected `HYPERVISOR`
   - the machine enrolls into Omni

## Operator-managed prerequisites

The provider can import a missing Talos image when `imageManagement.importOnMiss` is enabled and artifact/checksum URLs are configured. Preloading images is still supported and remains the fastest startup path.

Additional live-lab prerequisites:

- OpenNebula VM path must be functional on the target host.
- Do not rely on the provider to inject a CPU model. If your environment needs a specific CPU mode or model, keep it in the base OpenNebula template or a dedicated template clone for that environment.
- If you use a temporary public hostname such as `sslip.io` or `nip.io`, verify TLS issuance and firewall rules before starting the provider.

## Backend storage provisioning

This repository also ships a public Ansible workflow for preparing the Ceph backend and OpenNebula datastores used by the CSI driver.

Use:

- `deploy/ansible/opennebula-ceph/`

This workflow is intended for operator workstations and provisions:

- the Ceph cluster shape
- Ceph auth users for OpenNebula and CSI
- OpenNebula client-host Ceph materials and libvirt secret
- OpenNebula datastores matching the CSI driver metadata contract

It is documented at [/runbooks/ceph-opennebula-storage](/runbooks/ceph-opennebula-storage).
